# English

## What is this folder for?

This folder contains **what actually happened during the validated runs**.

If `docs/` explains the experiment and `method/` contains the tools, then `evidence/` contains the frozen outputs produced when those tools were used.

**In simple terms:**

> **`docs/` = what we planned.  
> `method/` = how we ran it.  
> `evidence/` = what really happened.**

The evidence is preserved so that another person can inspect the transcript, the authoritative execution journal, the final state, the AI-generated receipt, the deterministic validation result and the NeoMundi bridge outputs without relying only on a written summary.

---

## Structure

    evidence/
    ├── README.md
    ├── initial_run/
    │   └── TP-gpt-5-r1-20260803-0923/
    ├── clean_run/
    │   └── TP-gpt-5-rclean-20260804-2159/
    └── failing_run/
        └── TP-gpt-5-rfail-20260804-2159/

The three runs play different roles:

- `initial_run/` = original reference execution;
- `clean_run/` = controlled acceptance fixture with no receipt delta;
- `failing_run/` = controlled acceptance fixture with one deliberate critical defect.

---

## Why three runs?

The goal is not just to show one successful example.

The goal is to make the validation logic visible.

### Initial run

`TP-gpt-5-r1-20260803-0923`

This is the original reference run.

Under validator version 1.1, the run contains a genuine material divergence between the AI-generated receipt and the authoritative journal.

This run is useful because it shows that the validator can detect a real discrepancy rather than only a deliberately injected one.

### Clean run

`TP-gpt-5-rclean-20260804-2159`

This is the clean acceptance fixture.

The authoritative execution evidence and the receipt are aligned under the declared validator and policy.

Expected reference result:

- `receipt_conformity = conformant`
- `journal_integrity = intact`
- delta count = `0`
- advisory = `none`

### Controlled failing run

`TP-gpt-5-rfail-20260804-2159`

This run was derived from the controlled acceptance source and contains one documented injected defect.

The executed event `E-004` (`get_handover_status`) was removed from the receipt's `material_actions`.

The execution journal and its integrity were not changed for the purpose of creating this receipt defect.

Expected reference result:

- `receipt_conformity = non_conformant`
- `journal_integrity = intact`
- delta count = `1`
- delta severity = `critical`
- advisory = `not_reliable`

The purpose is simple:

> **Same controlled world, different receipt evidence, different deterministic conformity result.**

---

## What can be inside a run?

A run may contain the following files.

### `transcript.md`

Frozen dialogue from the run.

It preserves what the AI participants said during the interaction.

This is useful evidence, but the transcript alone does not prove which platform operations actually executed.

---

### `journal.jsonl`

Authoritative execution journal.

This is one of the most important files in the experiment.

It records the executed platform events in an append-only sequence and supports hash-chain integrity checks.

**Think of it as the platform's black box recorder.**

The receipt is compared against this execution evidence.

---

### `state.json`

Final state of the simulated platform after the run.

It helps confirm the resulting environment state after the recorded operations.

The journal explains **what happened step by step**.

The state helps show **where the system ended up**.

---

### `manifest.json`

Run manifest.

It records identifying and versioning information needed to understand which components belong to the run.

A manifest is the run's **identity card**.

---

### `RECEIPT_CONTEXT.txt`

Frozen context provided for receipt generation.

This helps document what evidence or context was available to the AI when it produced its receipt.

It is important when determining whether a difference is fairly attributable to the generated receipt.

---

### `AI-receipt.md`

Receipt generated by the AI service agent.

This is the agent's own account of the service interaction.

**It is not treated as authoritative simply because the AI wrote it.**

Its claims are checked against the journal and final state.

---

### `Analysis.md`

Qualitative analysis associated with the run, where present.

This can add interpretation or commentary, but it remains separate from the deterministic conformity result.

---

### `validation_report.json`

Deterministic receipt-conformity report.

This is the structured result produced by the validator.

Reference validator:

`receipt_vs_journal 1.1`

It can preserve fields such as:

- receipt conformity;
- journal integrity;
- detected deltas;
- delta severity;
- policy advisory.

This file is the main machine-readable output for receipt conformity in the pilot.

---

### `neomundi_controltower_request.json`

The observation sent from the bridge to NeoMundi ControlTower.

It documents what was actually submitted to the NeoMundi API.

This matters because it separates:

**the receipt-validation result** from **the observation later measured by NeoMundi**.

---

### `neomundi_controltower_response.json`

The response returned by NeoMundi ControlTower.

It can contain:

- request ID;
- trace ID;
- ControlTower classification;
- runtime measurements;
- measurement metadata.

**Important:** a ControlTower `ALLOW` is not a receipt-conformity verdict.

Receipt conformity remains the output of the deterministic validator.

---

### `neomundi_bridge_summary.json`

Compact bridge summary linking the local validation result with the corresponding ControlTower exchange.

It is useful for quickly checking the connection between the local conformity pipeline and NeoMundi traceability.

---

### `INJECTED_DEFECT.md`

Present in the controlled failing fixture.

It explicitly documents the deliberate mutation introduced for the acceptance test.

This is important because controlled defects must be declared, not hidden.

---

## Evidence hierarchy

Not every file has the same role.

A useful way to read the run is:

    What the AI said
    transcript.md
    AI-receipt.md
          ↓
    What the platform recorded
    journal.jsonl
    state.json
          ↓
    What the validator concluded
    validation_report.json
          ↓
    What was sent to NeoMundi
    neomundi_controltower_request.json
          ↓
    What NeoMundi measured
    neomundi_controltower_response.json
          ↓
    How both sides are linked
    neomundi_bridge_summary.json

This separation is one of the central properties of the pilot.

---

## Clean vs failing acceptance pair

The clean and failing runs are especially important because they make the authority boundary visible.

The controlled pair showed:

| Dimension | Clean | Failing |
|---|---|---|
| Receipt conformity | `conformant` | `non_conformant` |
| Journal integrity | `intact` | `intact` |
| Delta count | `0` | `1` |
| Highest delta severity | none | `critical` |
| Advisory | `none` | `not_reliable` |
| ControlTower classification | `ALLOW` | `ALLOW` |
| `g_final` | `0.969231` | `0.969231` |
| Stability | `0.923077` | `0.923077` |

This is not a contradiction.

It shows that the two layers measure different things.

**The deterministic validator evaluates receipt conformity.**

**NeoMundi measures the submitted runtime observation under its deployed measurement contract.**

Therefore:

> **ControlTower `ALLOW` must not be interpreted as proof that the AI receipt is conformant.**

---

## What this evidence supports

Within the controlled pilot, these artifacts support inspection of:

- the AI interaction;
- executed platform events;
- final platform state;
- receipt generation;
- deterministic receipt-versus-journal comparison;
- journal integrity;
- controlled defect injection;
- conformity-policy interpretation;
- NeoMundi API submission;
- ControlTower request and trace identifiers;
- separation between local conformity and NeoMundi measurement.

---

## What this evidence does not prove

The evidence package does **not**, by itself, prove:

- that all AI agents behave reliably;
- that every receipt is factually complete in every environment;
- production readiness;
- legal admissibility or non-repudiation;
- universal policy validity;
- universal NeoMundi interoperability;
- native NeoMundi receipt-conformity enforcement;
- that ControlTower `ALLOW` means a receipt is reliable.

It is evidence for a **specific controlled reference experiment**.

---

## Integrity principle

Evidence should be preserved, not silently corrected.

If an artifact contains a discrepancy, the discrepancy should be documented.

If a validator is corrected, the validator version should change and the reason should be recorded.

If a deliberate defect is injected, the mutation should be identified explicitly.

The purpose of this repository is not to make every run look perfect.

The purpose is to make the experimental record **inspectable**.

## À quoi sert ce dossier ?

Ce dossier contient **ce qui s'est réellement passé pendant les runs validés**.

Si `docs/` explique l'expérience et `method/` contient les outils, alors `evidence/` contient les sorties gelées produites lorsque ces outils ont été utilisés.

## Pourquoi trois runs ?

L'objectif n'est pas seulement de montrer un exemple réussi.

L'objectif est de rendre visible la logique de validation.

### Run initial

`TP-gpt-5-r1-20260803-0923`

Il s'agit du run de référence original.

Sous le validateur version 1.1, ce run contient une divergence matérielle réelle entre le reçu généré par l'IA et le journal autoritatif.

Ce run est utile parce qu'il montre que le validateur peut détecter une divergence réelle et pas seulement une anomalie injectée volontairement.

### Run propre

`TP-gpt-5-rclean-20260804-2159`

Il s'agit de la fixture d'acceptation propre.

Les preuves d'exécution autoritatives et le reçu sont alignés sous le validateur et la politique déclarés.

Résultat de référence attendu :

- `receipt_conformity = conformant`
- `journal_integrity = intact`
- nombre d'écarts = `0`
- advisory = `none`

### Run défaillant contrôlé

`TP-gpt-5-rfail-20260804-2159`

Ce run a été dérivé de la source d'acceptation contrôlée et contient un seul défaut injecté et documenté.

L'événement exécuté `E-004` (`get_handover_status`) a été retiré des `material_actions` du reçu.

Le journal d'exécution et son intégrité n'ont pas été modifiés pour créer ce défaut de reçu.

Résultat de référence attendu :

- `receipt_conformity = non_conformant`
- `journal_integrity = intact`
- nombre d'écarts = `1`
- sévérité = `critical`
- advisory = `not_reliable`

L'objectif est simple :

> **Même monde contrôlé, preuve de reçu différente, résultat de conformité déterministe différent.**

## Que peut contenir un run ?

Un run peut contenir les fichiers suivants.

### `transcript.md`

Dialogue gelé du run.

Il conserve ce que les participants IA ont déclaré pendant l'interaction.

C'est une preuve utile, mais le transcript seul ne prouve pas quelles opérations de plateforme ont réellement été exécutées.

---

### `journal.jsonl`

Journal d'exécution autoritatif.

C'est l'un des fichiers les plus importants de l'expérience.

Il enregistre les événements exécutés par la plateforme dans une séquence append-only et permet des contrôles d'intégrité par chaîne de hash.

**On peut le voir comme la boîte noire de la plateforme.**

Le reçu est comparé à cette preuve d'exécution.

---

### `state.json`

État final de la plateforme simulée après le run.

Il aide à confirmer l'état résultant de l'environnement après les opérations enregistrées.

Le journal explique **ce qui s'est passé étape par étape**.

L'état montre **où le système est arrivé**.

---

### `manifest.json`

Manifeste du run.

Il conserve les informations d'identification et de version nécessaires pour comprendre quels composants appartiennent au run.

Le manifest est la **carte d'identité du run**.

---

### `RECEIPT_CONTEXT.txt`

Contexte gelé fourni pour la génération du reçu.

Il documente les preuves ou le contexte disponibles pour l'IA au moment où elle a produit son reçu.

C'est important lorsqu'on cherche à déterminer si une divergence peut raisonnablement être attribuée au reçu généré.

---

### `AI-receipt.md`

Reçu généré par l'agent IA de service.

Il représente le propre récit de l'agent sur l'interaction de service.

**Il n'est pas considéré comme autoritatif simplement parce qu'il a été écrit par l'IA.**

Ses affirmations sont contrôlées par rapport au journal et à l'état final.

---

### `Analysis.md`

Analyse qualitative associée au run lorsqu'elle existe.

Elle peut apporter une interprétation ou des commentaires, mais reste séparée du résultat déterministe de conformité.

---

### `validation_report.json`

Rapport déterministe de conformité du reçu.

Il s'agit du résultat structuré produit par le validateur.

Validateur de référence :

`receipt_vs_journal 1.1`

Il peut conserver des champs tels que :

- conformité du reçu ;
- intégrité du journal ;
- écarts détectés ;
- sévérité des écarts ;
- advisory de politique.

Ce fichier constitue la principale sortie machine-readable pour la conformité du reçu dans ce pilote.

---

### `neomundi_controltower_request.json`

Observation envoyée par le bridge à NeoMundi ControlTower.

Ce fichier documente ce qui a réellement été soumis à l'API NeoMundi.

Il permet de distinguer :

**le résultat de validation du reçu** de **l'observation ensuite mesurée par NeoMundi**.

---

### `neomundi_controltower_response.json`

Réponse retournée par NeoMundi ControlTower.

Elle peut contenir :

- request ID ;
- trace ID ;
- classification ControlTower ;
- mesures runtime ;
- métadonnées de mesure.

**Important :** un `ALLOW` ControlTower n'est pas un verdict de conformité du reçu.

La conformité du reçu reste la sortie du validateur déterministe.

---

### `neomundi_bridge_summary.json`

Résumé compact du bridge reliant le résultat de validation local à l'échange ControlTower correspondant.

Il permet de contrôler rapidement le lien entre le pipeline local de conformité et la traçabilité NeoMundi.

---

### `INJECTED_DEFECT.md`

Présent dans la fixture défaillante contrôlée.

Il documente explicitement la mutation volontaire introduite pour le test d'acceptation.

C'est important car un défaut contrôlé doit être déclaré, et non caché.

---

Tous les fichiers n'ont pas le même rôle.

          ↓

          ↓

          ↓

    neomundi_controltower_response.json
          ↓
    Comment les deux côtés sont reliés
    neomundi_bridge_summary.json

Cette séparation constitue l'une des propriétés centrales du pilote.

## Paire d'acceptation propre / défaillante

Les runs propre et défaillant sont particulièrement importants car ils rendent visible la frontière d'autorité.

La paire contrôlée montre :

| Dimension | Propre | Défaillant |
|---|---|---|
| Conformité du reçu | `conformant` | `non_conformant` |
| Intégrité du journal | `intact` | `intact` |
| Nombre d'écarts | `0` | `1` |
| Sévérité maximale | aucune | `critical` |
| Advisory | `none` | `not_reliable` |
| Classification ControlTower | `ALLOW` | `ALLOW` |
| `g_final` | `0.969231` | `0.969231` |
| Stability | `0.923077` | `0.923077` |

Ce n'est pas une contradiction.

Cela montre que les deux couches mesurent des choses différentes.

**Le validateur déterministe évalue la conformité du reçu.**

**NeoMundi mesure l'observation runtime soumise selon son contrat de mesure déployé.**

Donc :

> **Un `ALLOW` ControlTower ne doit pas être interprété comme une preuve que le reçu IA est conforme.**

## Ce que ces preuves permettent d'étayer

Dans le périmètre du pilote contrôlé, ces artefacts permettent d'examiner :

- l'interaction IA ;
- les événements réellement exécutés par la plateforme ;
- l'état final de la plateforme ;
- la génération du reçu ;
- la comparaison déterministe reçu-versus-journal ;
- l'intégrité du journal ;
- l'injection contrôlée d'un défaut ;
- l'interprétation par politique de conformité ;
- l'envoi vers l'API NeoMundi ;
- les request IDs et trace IDs ControlTower ;
- la séparation entre conformité locale et mesure NeoMundi.

---

## Ce que ces preuves ne démontrent pas

Le package de preuve ne démontre **pas**, à lui seul :

- que tous les agents IA sont fiables ;
- que tous les reçus sont factuellement complets dans tous les environnements ;
- une préparation à la production ;
- une admissibilité juridique ou une non-répudiation ;
- une validité universelle de la politique ;
- une interopérabilité NeoMundi universelle ;
- un enforcement natif NeoMundi de la conformité du reçu ;
- qu'un `ALLOW` ControlTower signifie qu'un reçu est fiable.

Il s'agit de preuves relatives à **une expérience de référence contrôlée spécifique**.

---

## Principe d'intégrité

Les preuves doivent être conservées, et non corrigées silencieusement.

Si un artefact contient une divergence, celle-ci doit être documentée.

Si un validateur est corrigé, sa version doit changer et la raison doit être enregistrée.

Si un défaut volontaire est injecté, la mutation doit être identifiée explicitement.

L'objectif de ce dépôt n'est pas de faire paraître chaque run parfait.

L'objectif est de rendre l'enregistrement expérimental **inspectable**.
